## Implementation plan

> The S0–S6 sections below are the source of truth. The accepted-requirements list at the end of this section is an append-only review export; where a later "Replaces …" bullet supersedes an earlier one, the later bullet and the S-sections win.

### Problem

Sleep duration is far too long. 13 Nov: Sleep Detail said 10h 34m; the real night was asleep ~01:00–02:00, awake 05:50. Phase 1b already removed the hardcoded 23:10–06:30 window, so what's left is the band's own data plus our stitcher.

Measured on the real band dump (`tools/ble_verify/dump.db`, 550 sleep blocks, 2026-07-04 → 2026-11-12; 148 stitched sessions, 113 of them ≥ 3 h). The 13 Nov night itself is **not** in this dump (it ends 12 Nov 15:55).

| Fact | Evidence | Consequence |
|---|---|---|
| 18% of nights are **light-only** (0 deep, 0 REM) | 20 of 113 sessions ≥ 3 h [measured: dump.db]; e.g. 11 Nov 00:05–08:51, 526 min, every epoch stage 2 | Restorative share is 0, so the score is wrong on those nights. Light-only nights are **not** longer than staged ones (median 409 vs 443 min [measured]), so "light-only = lying awake" is unproven; the trim rule must work on staged nights too. |
| The band's window can run far past real wake | 13 Nov: band 10h 34m vs reality asleep ~01:00–02:00, awake 05:50 [user-stated, TODOS.md] | This is the bug. Which signal marks the real wake on such a night is unknown until we have that night's data. |
| Steps are recorded **only while walking** | 67 of 1,920 step rows fall between 01:00 and 05:00, 47 of them ≥ 20 steps [measured]; 11 Nov has none from 23:56 to 09:23 | A missing step row means "no data", not "no motion". A night-time step burst (bathroom) is not a wake-up if sleep evidence resumes after it. |
| HR is sampled **every 5 min** inside the band's sleep window, every 30 min otherwise | 11 Nov: 30-min samples until 00:40, 5-min from 00:40 to ~09:00. `hr_logs` starts 26 Oct [measured] | Dense night HR is the best independent signal. Nights before 26 Oct have no HR at all. |
| Sleeping HR ~50–56, single-sample spikes to 85–94 | 11 Nov 02:45 (94), 04:05 (94), 06:00 (90) [measured] | Single spikes are movements, not wake-ups. Wake needs a sustained rise. |
| The **noon extension fabricates stages** | `SleepAndReadinessEngine.kt:120-166`: when a session ends 11:40–12:10 it appends minutes until 17:00, inventing DEEP (HR ≤ baseline − 2) and REM (`minutes % 90 in 60..85`). `lowMotion` is true when no step row exists and `lowHr` is true when no HR sample is within 12 min. | Violates "real data only". Rare: 3 of 148 sessions qualify (20 Sep, 30 Sep, 25 Oct) [measured], but each can gain up to ~5 h of invented sleep. |
| 45-min gap merge | `stitchSleepSessions` merges blocks ≤ 45 min apart | Fine on its own; not the cause. |

Root cause: we treat the band's sleep window as truth, and there's no ground truth to check any fix against. The noon extension is a separate, rarer "invented data" bug.

### Goals

1. A night's duration is within 30 min of reality on nights the user labels (median), never worse than the band's raw number by more than 15 min.
2. The app never invents sleep stages. Light-only nights say so.
3. The user can correct a night in two taps, and that correction is the truth for scores.
4. Ship D5–D8 on top of trustworthy sleep, in an order where each piece needs only what's already shipped.
5. Scope limit: the refiner only **trims** the band window (later onset, earlier wake). It can't fix a window that's too short; only an EDITED label can lengthen a night.

2. **Light-only nights.** `StitchedSleepSession` gets `stagesAvailable: Boolean` (false when deep + REM = 0 across the session). `sleepScore` drops the restorative part and reweights the rest proportionally (duration 50, efficiency 12.5, regularity 18.75, timing 18.75) instead of scoring restorative as 0. Sleep Detail shows "Your band didn't record sleep stages this night" in place of the deep/REM/light breakdown; the hypnogram is hidden for that night. The coach context says "stages not recorded" instead of "Deep 0m, REM 0m" (`ClaudeCoachRepository.kt:38`).
3. **"Is this right?" + Edit times.** Sleep Detail gets a row under "Fell asleep · Woke": **Looks right** / **Edit**. Edit opens two time pickers (fell asleep, woke) prefilled with the shown values.
   - Table `sleep_labels(session_key TEXT PRIMARY KEY, onset TEXT, wake TEXT, kind TEXT /* CONFIRMED|EDITED */, band_onset TEXT, band_wake TEXT, created_at INTEGER)`. `session_key` = the band session's first-epoch timestamp (ISO, minute precision), so naps or fragments ending on the same date never collide. If a later stitch-rule change moves a session's start, a label with no exact key match attaches to the session it overlaps most. `band_onset`/`band_wake` record what the band said when the label was made, so EDITED-vs-band error can be measured later.
   - DB v4: `CREATE TABLE IF NOT EXISTS` in `onCreate` and in `onUpgrade` under `if (oldVersion < 4)`. `onDowngrade` is overridden as a no-op for future rollbacks (v5 → v4). It can't help a rollback **below** v4: the installed v3 helper has no override and `SQLiteOpenHelper.onDowngrade` throws. Rolling back past S1 needs `pull-phone-db.bat` first, then uninstall/`pm clear`, reinstall and restore from sterver (documented in the S1 checklist). `sleep_labels` is **not** added to `HISTORY_TABLE_COLUMNS` (upload, restore and `deleteSeedRows` iterate that map and filter on `raw_hex`, `LocalHealthDatabase.kt:492-526`).

   - An EDITED label sets the night to exactly [onset, wake]: band epochs outside are dropped; band stages inside are kept; minutes inside with no band epoch count as **asleep but unstaged**: they add to the total (so it matches what the user entered, Goal 3) but not to deep/light/REM, and they're left out of the restorative share's denominator, so no stage is invented (Goal 2).
   - A CONFIRMED label doesn't change times; it is recorded as ground truth and shown as "Confirmed by you".
   - Validation, one inline message per rule naming the value and limit, nothing saved: "Woke must be after Fell asleep."; "Night is 17h 10m; maximum is 16h.". An onset outside 18:00–12:00 (e.g. after a night shift) isn't refused: it asks "Outside usual night hours. Save anyway?".
   - `sleep_labels.kind` and `provenance` share one Kotlin enum source: `LabelKind { CONFIRMED, EDITED }`; `provenance = EDITED` iff the night has an EDITED label.
4. **Show both numbers.** When the shown night differs from the band's raw window by > 10 min, Sleep Detail adds "Band reported 10h 34m (00:05–09:44)".
   - `provenance` (one per night): `BAND` (band window as-is), `ADJUSTED` (S2 refiner moved a boundary), `EDITED` (user times).
   - `confirmed: Boolean` (a CONFIRMED label exists) and `stagesAvailable` are separate flags, not provenance values.
5. Coach context and the sterver summary upload already read `DayMetrics.sleep` (the summary upload re-sends the last 30 days), so they pick up corrected nights with no upload change.
6. Navigation: `SleepDetailView` gets `openEditor: Boolean`; the night index state lives in `ui/MainDashboardScreen.kt:208` (`sleepNightIdx`) and gains a "open Sleep Detail for session_key X with editor open" entry point used by S5.

### S2: Sleep boundary refiner + validation harness (effort M)

1. **Ground truth set.**
   - New `tools/pull-phone-db.bat`: `adb shell am force-stop com.jcwear.coach` first (so the DB, `-wal` and `-shm` are consistent), then `adb exec-out run-as com.jcwear.coach cat databases/jcwear_local_health.db` (plus `-wal`, `-shm`) into `tools/ble_verify/phone-<date>.db`, then `adb shell am start -n com.jcwear.coach/.MainActivity`: force-stop cancels the app's alarms and WorkManager jobs until it's opened again, which would stop background syncs and label collection. Debug builds are `run-as`-able.
   - Don't use `j2208_verify.py`: it needs the phone disconnected and its `--set-interval` defaults to 10, which reconfigures the band's sampling.
   - Labels come from the same DB (`sleep_labels`). Seed label for 13 Nov: onset 01:30 ±30, wake 05:50 (user-stated).
   - New `tools/make-sleep-fixture.py <phone.db>`: copies `sleep_blocks`, `hr_logs`, `step_logs` and `sleep_labels` for every labeled night, every light-only night (with and without dense HR), and the 10 most recent stage-rich nights before the first labeled night (a fixed rule, so the set is reproducible) into `android-app/app/src/test/resources/sleep/fixture.db`. That file stays **out of git** (`.gitignore:24` ignores `*.db`; it is real health data). `SleepAccuracyTest` uses `Assume` to skip when it's missing, so CI and clones stay green.
   - Committed instead: synthetic minute-series fixtures built in Kotlin test code for every refiner rule (below).
2. **`domain/SleepBoundaryRefiner`** (pure Kotlin, no Android, no logging): `refine(session, hr: List<Pair<LocalDateTime, Int>>, steps, label?) -> RefinedSleep(onset, wake, epochs, provenance, confidence, onsetRule, wakeRule, trimmedLeadMin, trimmedTailMin)`.
   - Dense HR = samples ≤ 6 min apart. Personal sleeping HR = median of the lowest 50% of the session's dense samples; wake threshold = sleepingHr + 10 bpm. Both constants live in one `SleepRules` object, tuned on labeled nights.
   - **Sleep evidence** = a deep/REM epoch, or a run of ≥ 3 consecutive dense HR samples ≤ threshold.
   - **Onset** = the first sleep evidence in the band window. Leading minutes before it are trimmed. No evidence at all (no dense HR, no stages): keep band start, confidence LOW, `onsetRule = bandKept`.
   - **Exit event** = a sustained HR rise (≥ 2 consecutive dense samples > threshold + 5) or a step record with ≥ 20 steps.
   - **Wake** = the first exit event that comes **after at least one piece of sleep evidence** and has **no sleep evidence after it** inside the band window; minutes after it are trimmed (`wakeRule = hrRise | steps`). If there's no such event, wake = the end of the last sleep evidence when dense HR continues past it without another low run (`wakeRule = lastEvidence`), else the band end (`wakeRule = bandKept`). A 03:00 bathroom trip followed by low HR is an exit event with sleep evidence after it, so it never ends the night. A night with **no sleep evidence at all** (no dense HR and no deep/REM, e.g. every light-only night before 26 Oct) keeps the whole band window: exit events can't set wake there (`onsetRule = wakeRule = bandKept`, confidence LOW). Without this, 5 Oct (light-only, 00:49–10:40) would be cut at 01:27.
   - Single HR spikes never trim or split anything.
   - Structure: `onset()`, `wake()` and `confidence()` are separate functions (≤ 5 branches each). HR is sorted once; per-session lookups use binary search on time, not a scan of all 90 days.
   - Confidence (per night): HIGH when both boundaries were set by evidence and stages and HR agree within 20 min where both exist; MEDIUM when at least one boundary was set by evidence; LOW when both were `bandKept`.
   - An EDITED label overrides everything (provenance EDITED, confidence HIGH, rules `label`).
3. **Wiring** (`buildDaySeries`), in this order: (1) stitch; (2) apply labels, always, whatever the flag; (3) refine only if `sleepAutoAdjust` is on and the night isn't EDITED (the refined result is always computed for logging and the harness, but used only then); (4) pick main sleep from the result of steps 2–3. With the flag off, output equals S1's byte-for-byte (test). `startTime`/`endTime`/`totalSleepMin`/stage counts become the chosen values (they drive regularity via `midpoint`); band values move to `bandStart`/`bandEnd`/`bandTotalMin`. The day key stays the **band** session's `wakeDate`, so a trim or edit never moves a night to another day. Naps stay out of the score as today.
4. **Validation harness** `SleepAccuracyTest` (JVM): runs stitch + refine over `fixture.db` and prints a per-night table. Errors are measured per boundary: **|onset error|** and **|wake error|** in minutes (refined vs label, band vs label), plus window length. A night shifted 90 min later must not score zero. The table reports CONFIRMED and EDITED nights separately. Asserts:
   - median |onset error| ≤ 30 min and median |wake error| ≤ 30 min on gate nights (EDITED, plus CONFIRMED-of-BAND; CONFIRMED-of-REFINED is context only);
   - no labeled night where either refined boundary error exceeds the band's by more than 15 min;
   - the named 13 Nov assertion from S0 (when S0 says the band data can see it);
   - stage-rich unlabeled nights move ≤ 20 min, except moves set by an exit event (`wakeRule = steps | hrRise`), which are allowed but printed in the per-night table for review (e.g. 11 Oct ~35 min and 25 Oct ~51 min are trimmed by a step burst after the last REM);
   - the synthetic fixtures each hit their rule (light-only night with an HR rise at 06:00 → wake 06:00; 03:00 step burst then low HR → wake unchanged; no dense HR → band kept, LOW; light-only night with no HR and a 01:27 step burst → band window kept; stage-rich night → unchanged within 20 min);
   - every pre-26-Oct light-only night in the fixture keeps its band window.
5. **Ship gate:** the refiner always runs, but its result replaces the band window only when `AppSettings.sleepAutoAdjust` is true. It defaults to false and S2's code ships with it false (the refined window is still logged and used by the harness). The release that flips the default to true ships only when the harness passes on ≥ 7 labeled nights **of which ≥ 3 are EDITED nights where the band was off by > 30 min** (13 Nov counts). CONFIRMED-only nights mostly agree with the band, so on their own they can't prove the over-long-window bug is fixed. S6 doesn't depend on this gate (it uses trusted nights, S6). Labels are collected through S5's notification actions, so S2's checklist turns the morning notification on. Timebox: if there are fewer than 7 labels after 14 days, review the harness table with what exists and decide then; S1's manual edit remains the fix in the meantime.
6. **Refiner log line:** `DailySeriesRepository.load` (Android side, not the pure refiner) logs one `Log.i("SleepRefiner", ...)` line for **the latest night only**, and only when its result differs from the last logged one: wake date, band window, refined window, confidence, `onsetRule`, `wakeRule`.
7. **Sleep Trends marks provenance** (`ui/SleepTrends.kt`): in the bedtime/wake range chart, EDITED nights get a solid outline and LOW-confidence nights a dashed one, with a one-line legend. No new screen.

### Developer tooling contract (S0, S2)

The tuning loop, copy-paste, from the repo root in **cmd** (not PowerShell 5.1: its `>` re-encodes binary output and corrupts the DB):

```
tools\pull-phone-db.bat
python tools\make-sleep-fixture.py tools\ble_verify\phone-2026-11-20.db
android-app\gradlew -p android-app :app:testDebugUnitTest --tests "*SleepAccuracyTest" -PrequireSleepFixture
```
The report lands in `android-app/app/build/reports/sleep-accuracy.md` (the test prints that path; Gradle hides test stdout).

`tools/pull-phone-db.bat [-s <serial>] [--out <path>] [--force]`:
- Honors `ANDROID_SERIAL` / `-s`. Non-interactive: no `pause`, no prompts; an existing output file is an error unless `--force`.
- Date for the default name comes from `powershell -NoProfile -Command Get-Date -Format yyyy-MM-dd` (not locale-dependent `%date%`). Copies are named `phone-<date>.db`, `phone-<date>.db-wal`, `phone-<date>.db-shm` so SQLite replays the WAL; a missing `-wal` is skipped with a note.
- Validation before success: first 16 bytes are `SQLite format 3`, `PRAGMA integrity_check` is `ok`, and it prints the `sleep_blocks` row count and newest `device_time` (python stdlib). `run-as` errors land in stdout, so this check is the only reliable signal.
- Every exit path (success or failure) runs `am start` first (`goto :relaunch`) and prints `app relaunched` or `RELAUNCH FAILED: run adb shell am start -n com.jcwear.coach/.MainActivity`.
- Failures: `exit /b 1` with one stderr line naming the step, the file and the fix (e.g. `run-as refused: install a debug build with gradlew installDebug`; `no device: connect the phone and accept USB debugging`; `adb not found: add platform-tools to PATH`).
- `/?` prints usage with an example and the output path.

`tools/make-sleep-fixture.py <phone.db> [--out <path>]`:
- Output path resolved from the script's own location, not the cwd.
- `PRAGMA user_version < 4` (no `sleep_labels`) → exit 2: `phone DB is schema v3: install the S1 build and collect labels first`. For S0 (before S1) the analysis uses the pulled DB directly; the fixture script is only for S2.
- 0 labeled nights → exit 1 with the same kind of message. Otherwise prints `labeled N (EDITED x, CONFIRMED y), light-only N, stage-rich N`.
- `-h` prints usage.

`SleepAccuracyTest`:
- `Assume` message names the fix: `fixture.db missing: run tools/pull-phone-db.bat then tools/make-sleep-fixture.py`. With `-PrequireSleepFixture` (used for the gate run) a missing fixture is a failure, not a skip.
- A fixture with 0 labeled nights fails (never passes vacuously).
- `SleepRules` constants can be overridden with system properties (`-Dsleep.wakeDelta=12`, `-Dsleep.riseDelta`, `-Dsleep.lowRun`, `-Dsleep.stepBurst`, `-Dsleep.denseGapMin`); the report starts with the values in effect.
- The report's last line is `GATE: PASS|FAIL (labeled=N/7, edited_off30=M/3)`. It's informational; the run doesn't fail on it.

`sleepAutoAdjust` is reachable without a rebuild: Settings → Data → "Adjust sleep times using heart rate (beta)", shown in debug builds until the gate flips, then in all builds.
